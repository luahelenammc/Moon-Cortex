# Finance Capability Map

**Module:** Moon Cortex · Financial Living System  
**Bootstrap:** Adaptive Finance Bootstrap  
**Version:** `0.1.0-pre.3`  
**MSL:** 4.3

The bootstrap does not ask the user to choose technical capability names. It observes the financial field, identifies the missing capability and compiles the smallest adequate form.

> **Access ≠ activation.**

## Core capabilities

| Capability | Activate when | Minimum result |
|---|---|---|
| Financial Reality Gate | Always, proportionately | Separate what is observed, supplied, unknown and materially needed |
| Current Financial State | A living or repeatable finance context exists | Current liquid position, protected money, liabilities, receivables and governing risks |
| Cycle Reconciliation | Money enters or leaves across a defined cycle | Opening-to-closing equation with visible difference when it does not close |
| Temporal Ownership | Income, advances or commitments cross periods | Economic ownership separated from visibility date |
| Reserve Semantics | Money has named purposes or protected envelopes | Protected, conditional and flexible money excluded or included correctly |
| Double-Count Guards | More than one representation of an obligation exists | One economic event mapped across cash, liability, reserve and reimbursement without duplication |
| Cycle Closing and Carryover | A cycle ends and another begins | Closed truth, retained open commitments and clean next-cycle opening |
| Epistemic Typing | Evidence strength affects a decision | Fact, calculation, inference, estimate, recommendation and pending confirmation remain distinct |

## Conditional capabilities

| Capability | Evidence that earns activation | What it adds |
|---|---|---|
| Credit Card Intelligence | One or more cards materially shape cash or future obligations | Gross traffic, amount due, ownership, timing and liability view |
| Installment Tail Engine | Installments or equivalent future payment tails exist | Remaining burden, end date, next-cycle pressure and tail visibility |
| Replacement Test | An expiring burden may be replaced by a new one | Whether relief becomes real capacity or is mostly reoccupied |
| Microfrequency / Swarm Analysis | Repeated low-salience events obscure the pattern | Aggregation by function, vendor or interval without automatic waste judgment |
| Next-Cycle Anticipation | Open statements or known future commitments affect today's decision | Observed, contractual and expected future ground kept separate |
| Income Advance Protection | An advance or irregular inflow protects a later period | Future-period envelope and current-use limit |
| Third-Party and Reimbursement Ledger | The user pays for or receives money from others | Economic owner, competence, status, destination and duplicate control |
| Shared-Cost Ledger | Household or shared obligations need explicit allocation | Split rules, responsible parties, carryover and settlement state |
| Debt Schedule | A non-card debt has a finite or recurring schedule | Creditor, principal, cost, payment rhythm, remaining obligations and close condition |
| Irregular Income Layer | Income varies in amount or timing | Confirmed versus uncertain inflow, buffers and cycle adaptation |
| Multi-Currency Layer | More than one currency materially affects liquidity | Currency-aware balances and explicit conversion rate/source/date |
| Tax Reserve Layer | A known tax or statutory obligation requires ring-fenced liquidity | Reserve purpose, due cycle and current-rule verification boundary |
| Subscription Intelligence | Recurring services materially affect pressure or duplication | Recurrence, renewal, overlap and decision checkpoints |

## Routing examples

### Simple salaried user

Compile the core capabilities and a compact current-state/cycle structure. Omit card, installment, multi-currency and shared-cost machinery unless evidence appears.

### Credit-heavy user

Compile card, installment and likely next-cycle capabilities. Add microfrequency analysis only when repetition is part of the user's actual friction. Add reimbursement or shared-cost capability only when economic authorship crosses people.

### Irregular multi-currency user

Compile irregular-income and multi-currency layers, plus reserve or tax capability only if a named obligation exists. Do not assume any country's payroll or tax terms.

### Existing governed system

Map equivalent responsibilities first. Integrate missing capabilities into the existing authority structure; do not create a parallel Moon-shaped system merely because the bootstrap has a tidy tree.

## Deactivation and review

A capability may be demoted when:

- the underlying instrument or obligation no longer exists;
- the user no longer needs the analysis;
- the capability creates more maintenance than clarity;
- the host cannot maintain its required state;
- a safer smaller form now carries the responsibility.

Deactivation preserves historical evidence. It does not erase past events.

## Public boundary

Capability names are public abstractions. Implementation-specific thresholds and private donor internals are outside the public contract unless explicitly documented here.
