# Public Editorial Policy

**Public documentation explains available capabilities, how to use them, what evidence supports them, and which real permissions or limits apply.** It is not a diary of editorial selection, unpublished designs or upstream working history.

## Publication rule

1. **Capability first.** Describe the public module's purpose, inputs, output, first use, scope, supported status and concrete limitations.
2. **No backstage narration.** Do not insert private project names, internal origin stories, unpublished feature inventories, hypothetical promotion plans, selection/extraction notes or explanations of why a feature was not released.
3. **Present the current public product.** A module index lists documented and available routes. Do not fill empty slots with speculative candidates.
4. **Preserve necessary truth.** Disclose what a user needs for consent, identity, data privacy, license compliance, genuine third-party creative credit, tool availability, empirical status and safe use. Experimental status is relevant to the capability itself.
5. **Keep release history factual and concise.** Changelogs describe visible public changes, without recounting internal source reviews or private experiments.
6. **Separate contributions from presentation.** Maintainer-facing review can enforce this policy, but public landing pages must not explain internal editorial workflow.

## Review gate

Before publishing or updating user-visible Markdown, ask:

- Can someone understand and use this artifact without learning its unpublished ancestry?
- Is each limitation actionable or relevant to user consent, tool availability, evaluation or safe use?
- Does any sentence inventory unavailable ideas, name unpublished source systems or justify not releasing them?
- Does attribution credit actual public third-party influence without exposing unrelated work?
- Are canonical links, package bytes, titles and source permissions still correct?

If a sentence merely narrates internal decisions, remove it. If it is a necessary restriction, rewrite it as a user-facing capability or permission statement. Review the entire page after removing a heading or list to avoid orphaned references.

The automated editorial check rejects known disclosure patterns on defined public browse surfaces; human review remains responsible for meaning. This policy does not relax applicable licenses, consent or evidence standards.
